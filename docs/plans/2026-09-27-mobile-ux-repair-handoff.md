## 1. 이번 작업이 해결해야 하는 사용자 경험

> 홈에서 내 계정을 쉽게 찾고 → 지출을 입력하고 → 저장 여부를 정확히 알며 → 기록한 날짜의 캘린더에서 거래를 확인한다. 계획을 만들 때 모든 입력칸이 화면 안에 들어오고, 내가 검토한 내용만 확정된다.

핵심 완료 조건:

1. 프로필 진입점이 홈 **우측 상단**에 있고 실제 설정 화면으로 이동한다. 본문을 덮는 사람 장식과 `장부지기` 표현은 사용자 노출 영역 전체에서 제거된다.
2. 일반 모드에서 저장이 확인된 거래는 기록 날짜의 캘린더와 일별 목록에 정확히 한 번 표시된다. 저장 성공과 부가 조회 실패를 구분한다.
3. iPhone에서 계획의 날짜·금액·단위가 카드 밖으로 나오지 않는다. 제목과 진행 막대, 입력칸 사이가 불필요하게 벌어지지 않는다.
4. 홈·장부·계획·리포트·설정·온보딩·거래 상세에 같은 여백, 필드, 제목, 버튼 규칙을 적용한다.
5. 계획 변경 후 이전 미리보기로 확정할 수 없다. 설정에서 예산·목표를 실제로 수정할 수 있다.

## 2. 현재 증거와 확실성

### 2.1 사용자 스크린샷

- S1: 홈의 중앙 오른쪽 사람 아이콘/라벨이 소개 문장을 가림. 큰 제목, 긴 모드 배지, 안내 카드가 실제 기록보다 많은 공간을 차지함.
- S2: 거래 입력 폼 아래에 일반적인 저장 실패 메시지. **사진만으로 POST 실패인지 후속 조회 실패인지 알 수 없고, 금액 입력값도 잘려 있어 유효성을 판단할 수 없다.**
- S3: 계획 1단계 날짜 입력이 카드 우측을 넘음. 원 단위가 입력 테두리 밖에 붙고 폼 내부 여백이 없음. 상단 공백이 과도함.

사용자의 실제 금액·계정값은 이 문서나 진단 테스트에 복사하지 않았다. 테스트에는 기존 저장소의 합성 fixture만 사용했다.

## 4. 화면별 목표 구조

### 4.1 홈

권장 구조:

```text
장부 AI                              [내 프로필]
오늘 날짜                       [할머니 모드: 켜짐] ← 켰을 때만 보조 표시

[ 이번 달 지출 / 계획상 남은 생활비 ]
  가장 중요한 금액
  예산·기간·입력 기준의 짧은 설명

[ 계획 없음: 생활비 계획 만들기 > ] 또는 [ 계획 확인 > ]

최근 내역                         전체 보기
거래 목록 / 첫 거래 안내 + 지출 기록하기

저축 목표                         N% 달성
이번 주 소비 안내                 데이터가 있을 때만 요약

                           [+ 거래 기록]
홈          장부          계획          리포트
```

- 홈 제목은 `장부 AI`, 최상단 오른쪽 44px 프로필 버튼은 `/settings`로 연결하고 접근성 이름은 `내 프로필 및 설정`으로 한다.
- `useAuth().avatarUrl`이 있을 때만 사진을 사용한다. 없거나 로딩 실패면 공통 기본 아이콘을 사용한다. 사진을 얻으려고 카카오 선택 동의를 추가로 요청하지 않는다.
- 프로필을 본문에서 이동하는 것이 아니라 **장식 제거 + 실제 프로필 진입 추가**다. 모드 변경은 설정에서 제공한다. 모드가 켜져 있을 때 홈에 작은 상태/설정 링크를 유지한다.
- 계획이 있으면 기존 계획 금액 정의를 유지해 `계획상 남은 생활비`를 중심에 둔다. 부족하면 `생활비 N원 부족`으로 표현한다.
- 계획이 없으면 작은 월 지출 요약과 계획 설정 진입을 제공한다. 거대한 “계획부터 세워요”가 첫 기록을 밀어내지 않게 한다. 계획 없이 기록 가능한 현재 기능을 유지한다.
- 목표 문구 `목표까지 30%`처럼 남은 비율인지 달성률인지 모호한 표현은 `30% 달성`으로 바꾼다. 실제 수치만 계산해 넣는다.
- AI 안내는 기록이 충분할 때 내용을 보여준다. 빈 장부에서는 여러 안내 박스 대신 `아직 기록이 없어요` + `지출 기록하기`를 한 곳에 둔다.
- FAB를 유지하되 마지막 행/내역 버튼 위를 덮지 않는 하단 여유 공간을 둔다. 폼에는 FAB를 표시하지 않는다.

### 4.2 거래 입력 → 저장 → 캘린더

```text
[뒤로]           거래 기록
             지출 / 수입 / 이체

금액
[                 9,600 원 ]
분류        [식비               v]
계좌        [현금               v]
날짜        [2026. 07. 12.       ]
사용처      [선택 입력           ]
메모        [선택 입력           ]
[ ] 생활비 예산에서 제외

필드 오류 또는 저장 결과 안내
[ 지출 저장하기 ]
```

- 기본 말투는 존댓말. `얼마 썼어?` 대신 `지출 금액` / `수입 금액` / `이체 금액`으로 통일한다.
- 금액 숫자는 크지만 58–74px 고정에 가깝게 늘리지 않는다. 긴 금액에서도 원 단위와 전체 값이 읽혀야 한다.
- `사용처·메모` 텍스트 입력 옆의 이동 화살표는 제거한다. 선택 목록은 아래 방향 선택 아이콘으로 구분한다. 아이콘 자체가 별도 버튼인 것처럼 만들지 않는다.
- 선택 정보는 기본 노출하되 낮은 위계로 표시한다. 별도 화면이나 무조건 필수 입력으로 늘리지 않는다.
- `수기 입력` 배지와 매번 반복되는 “기록하면 AI가 …” 대형 박스는 제거한다. 켜진 할머니 모드에서만 다음 단계가 있음을 한 줄로 알린다.
- 저장 버튼은 유형별 `지출 저장하기` / `수입 저장하기` / `이체 저장하기`. 저장 중 `저장 중…`, 중복 탭 방지. 폼 키보드 제출도 동일 함수 사용.
- 일반 모드 성공 경로는 **서버 저장 확인 → 해당 거래를 ID 기준으로 갱신 → 기록일의 캘린더 → 일별 내역에 새 거래 강조 → 짧은 성공 안내**다.
- 기존 opt-in 할머니 모드는 저장 후 이유 질문을 유지한다. 이 모드도 거래는 이미 저장됐음을 알리고, 이유 완료/나중에 답하기 이후 동일 거래 날짜의 캘린더로 돌아갈 수 있게 한다. 일반 모드에 이유 질문을 끼워 넣지 않는다.

### 4.3 생활비 계획 만들기·수정

```text
[이전]       생활비 계획                    1 / 3
기간과 예산을 정해 주세요
━━━━━━──────────────

[ 카드: 내부 여백 16~20 ]
  시작일
  [ 날짜 입력                       ]
  종료일
  [ 날짜 입력                       ]
  이번 기간 생활비
  [                         0   원 ]
  예정 지출을 포함한 총금액이에요.

[ 다음: 우선순위와 예정 지출 ]
```

- 단계 순서 1 기간·예산 → 2 우선순위·예정 지출 → 3 검토·확정은 유지한다.
- 모든 콘텐츠는 위에서 자연스럽게 쌓는다. 화면 높이만큼 행을 벌리는 grid stretch를 없앤다.
- 날짜와 금액 모두 동일한 필드 높이·테두리·여백을 사용한다. 금액의 `원`은 **같은 테두리 안**에 둔다.
- 날짜 필드는 native date를 유지하고 폭 문제를 해결한다. 검증 없이 별도 날짜 선택 라이브러리를 도입하지 않는다.
- 안내 문구는 `예정 지출을 포함해 이번 기간에 쓸 생활비를 입력해 주세요.` 수준으로 짧게 한다. “수입에서 자동 추정하지 않아요” 같은 내부 설계 설명은 기본 화면에서 제거한다.
- 기존 월 예산을 가져왔다면 `저장된 월 예산을 불러왔어요. 이 기간에 맞게 확인해 주세요.`로 출처를 표시한다. 실제 저장 값이 없으면 예시 금액을 채우지 않는다.
- 시작일 ≤ 종료일, 서버가 허용하는 기간 길이, 예정 지출의 기간 내 날짜, 양의 정수 금액을 각 단계에서 검증한다. 서버와 다른 임의 최대값을 만들지 않는다.
- 단계 2에서 최대 3개를 조용히 잘라내지 않는다. 초과 입력을 명시하고 수정하게 한다. 새 예정 지출을 작성 중인데 추가하지 않고 다음을 누르면 “추가” 또는 “작성 취소”를 선택하게 하여 입력을 조용히 버리지 않는다.
- 뒤로 가기/탭 전환/새로고침 시 계정별 초안을 복원한다. 기존 `local-drafts.ts` 정리 정책에 계획 초안을 포함한다. 로그아웃·계정 전환·전체 데이터 삭제 때 혼입되지 않게 한다.
- 검토 단계는 **현재 초안 + 현재 기준 버전**의 성공한 미리보기가 있을 때만 확정 가능하다. 이전 결과를 재사용해 활성화하지 않는다.
- 계획 상세 카드에도 16~20px 내부 여백을 적용한다. 주차·예정 지출·실제 거래 연결은 긴 이름에서 세로 배치로 전환한다.

### 4.4 장부 캘린더

- `YYYY-MM-DD` 선택일을 URL 상태로 전달한다. 표준 복귀 URL 제안: `/ledger?date=2026-07-12&view=calendar`. 월은 유효한 date에서 파생한다. `demo=1` 보존은 기존 `withDemo()`로 처리한다.
- 저장 복귀 때 새 거래를 숨기는 검색어/필터는 해제한다. 일반 탐색에서는 사용자가 고른 월·필터를 유지한다. “저장 후 복귀”와 “평소 탭 탐색”을 구분한다.
- URL 날짜가 없으면 이번 달 오늘을 우선 선택하고, 사용자가 월을 옮기면 유효한 선택일을 유지한다. 존재하지 않는 날짜는 안전한 날짜로 복구한다.
- 월 제목·수입/지출 요약·캘린더·선택일 내역을 먼저 노출한다. 현재 항상 펼쳐진 검색/필터 3개는 `검색·필터` 버튼 아래로 접고 활성 조건 수를 표시해 달력을 아래로 밀어내지 않는다.
- 7열 캘린더에는 큰 금액을 축약하고 전체 값은 해당 날짜 목록과 접근성 이름에서 읽게 한다. 색상만으로 수입·지출을 구분하지 않는다.
- 새로 저장한 거래의 선택일 강조와 일별 목록 노출을 검증한다. 페이지 진입 시 무조건 맨 위로만 스크롤하는 기존 router 동작과 충돌하지 않게, 캘린더/목록 안내 위치를 정한다.
- 상세 수정/삭제 후에도 원래 날짜로 돌아온다. 거래 날짜를 수정한 경우 새 날짜로 복귀한다.

### 4.5 설정·프로필·온보딩

- 설정 상단은 계정 정보, 아래는 `예산과 목표 / 계좌·분류 / AI 말투 / 데이터 관리` 묶음으로 정리한다. 현재 기능만 노출한다.
- 기존 사용자의 수정 경로를 `/settings/budget`, `/settings/goal`로 분리한다. 공유 필드는 재사용할 수 있으나 온보딩 route guard를 느슨하게 풀어 해결하지 않는다.
- 편집은 서버에 저장된 profile로 시작하고 변경한 부분만 합쳐 저장한다. 취소는 원본을 보존한다. 첫 소개 완료 상태를 되돌리지 않는다.
- `데이터 방식`은 현재 `직접 입력` 상태 설명으로 바꾸고, 준비 중인 계좌 연결을 동작 가능한 메뉴처럼 보이지 않게 한다.
- 신규 실제 계정은 빈 입력 draft와 명시적인 0/미입력 구분을 사용한다. UI draft와 유효한 `Profile` 타입을 구분해 검증한 뒤 변환한다. `demoProfile`은 명시적 데모에서만 사용한다.
- 예산 화면은 총 보유 자산과 매달의 흐름을 구분한다. 고정지출·상환·생활비의 중복 포함 여부를 짧게 설명한다. 월 수입−고정지출−상환−생활비는 `입력한 금액 기준 월 잔여 예상`이고 저축 확정액이라고 약속하지 않는다. 음수는 부족액으로 표시한다.
- 기존 사용자에게 이미 저장된 값을 데모처럼 보인다는 이유로 삭제하거나 일괄 초기화하지 않는다.

### 4.6 리포트·상세·공유

- 리포트는 숫자 → 차트/분류 → 한 줄 해석 순서. 큰 금액, 긴 카테고리, 데이터 없는 달에도 카드가 넘치지 않아야 한다.
- 계획 리포트의 `원래 계획 / 현재 계획 / 실제 지출` 구분과 음수 부족분을 유지한다. 예산 인상을 개선으로 표현하지 않는다.
- 상세의 저장·삭제·평가도 거래 저장과 동일하게 “변경 성공/후속 조회 실패”를 분리한다. 모달은 키보드·스크롤·포커스 복귀까지 점검한다.
- 공유 UI와 Canvas 내 `장부지기의 한마디`를 `장부 AI 소비 리포트`로 함께 변경한다. 기존 민감정보 제외 정책은 그대로 둔다.
- `숫자는 장부 코드가 계산했어요`, 버전 `vN` 같은 구현 설명은 주요 화면에서 제거한다. 사용자에게 필요한 `입력한 내역 기준`과 실제 계산 기준은 유지한다.

## 5. 공통 디자인 및 CSS 구현 기준

기존 색상·12px 카드 반경은 유지한다. 명시한 수치는 시작 기준이고 큰 글자에서 높이를 고정하지 않는다.

| 항목 | 구현 기준 |
|---|---|
| 화면 수평 여백 | 320–370px에서 16px, 그 이상 모바일 20px |
| 카드 | 내부 16–20px, border 1px, radius 12px, 기본 그림자 없음 |
| 섹션 간격 | 24px, 폼 필드 간 16px, label↔input 6–8px |
| 일반 화면 제목 | 24–28px, line-height 1.3, 필요한 경우 줄바꿈 |
| 주요 금액 | 기본 32–40px, 긴 값은 24–32px 또는 넓은 전용 행. 금액 자체를 잘라내지 않음 |
| 본문/입력 | 16px 기준, 설명 13–14px, line-height 1.45–1.6 |
| 터치 영역 | 프로필·이전·닫기 최소 44×44 CSS px, 주요 버튼 min-height 52px |
| 숫자 | `font-variant-numeric:tabular-nums`; 원 단위와 그룹화를 일관되게 유지 |
| 필드 | width/max-width 100%, min-width 0, input/select/textarea 동일한 테두리 규칙 |
| 레이아웃 | 축소 가능한 열 `minmax(0,1fr)`, 자식에도 min-width 0, 빈 공간은 콘텐츠 흐름으로 처리 |

CSS 수정 지침:

1. `.home-hero .bookkeeper`와 잔존 장식 전용 위치 규칙을 제거한다. 제목 옆 margin을 임의로 늘리는 임시 처방을 하지 않는다.
2. `.plan-screen`에 `align-content:start`를 적용하고 내용 높이 기준의 행 배치를 검증한다. `.plan-form`, `.plan-review`, 계획 상세 surface의 내부 여백을 명시한다.
3. `.plan-form > label`, 날짜 입력에 `min-inline-size:0`, `inline-size:100%`, `max-inline-size:100%`를 적용하는 방향으로 검증한다. 필요 시 WebKit 날짜 편집 내부의 최소 폭·정렬을 좁게 조정한다. 클릭 영역과 날짜 선택 접근성은 보존한다.
4. `CurrencyInput`에 폼 전용 variant/class를 두고 **외부 래퍼 한 곳에** border/padding을 둔다. input은 `flex:1 1 0; width:0; min-width:0`, 단위는 `flex:0 0 auto`. 현재 `.plan-form input`의 범용 border와 `.currency-input` 밑줄이 이중으로 적용되지 않게 선택자를 분리한다.
5. `overflow-x:hidden`, 화면 전체 scale/zoom, 아주 작은 글씨로 잘림을 숨기지 않는다. 카드 내부 자식의 경계도 측정한다. 문서 scrollWidth만 같다고 통과가 아니다.
6. 긴 값이 있는 행은 필요한 폭에서 label/value를 2행으로 바꾼다. 텍스트 말줄임은 가맹점 같은 보조 문자열에만 적용하고 전체 내용은 상세에서 제공한다.
7. `.primary-button:disabled`를 모든 상황에서 `cursor:wait`로 만들지 않는다. 입력 미완료와 저장 중 상태를 구분하고 왜 진행할 수 없는지 필드에 설명한다.
8. native safe area와 CSS `env(safe-area-inset-bottom)`을 각각 측정한다. iPhone에서 두 번 더하지 않는다. 임의의 기기별 상수 padding을 추가하지 않는다.
9. 거래 폼에서 하단 버튼은 우선 문서 흐름 안에 둔다. 고정 버튼이 필요하면 키보드·홈 인디케이터·마지막 입력칸과의 충돌을 실기기로 검증한 뒤 적용한다.

## 6. 저장 문제: 반드시 지켜야 하는 처리 계약

### 6.1 먼저 운영 실패를 분류한다

기존에 실패한 거래를 재저장하기 전에, 가능한 인증된 읽기 경로에서 실제 거래 존재 여부를 확인한다. 테스트를 위해 사용자 계정에 임의 거래를 생성하지 않는다. 로컬/테스트 계정은 합성 데이터로 수행한다.

관찰할 최소 정보: 요청 path/method, status, 안전한 error code, correlation ID, 시작~응답 시간, transaction ID 반환 여부. 토큰·요청/응답 전체 body·실제 금액·상호·메모를 로그나 문서에 남기지 않는다.

```text
POST /transactions
 ├─ 유효한 201/202 + transaction → 저장 확인
 │   ├─ summary/plan 성공 → 캘린더와 지표 갱신
 │   └─ summary/plan 실패 → 거래는 유지, 해당 지표만 재시도 안내
 ├─ 400/401/409/429 → 실제 code별 안내와 복구 동선
 └─ timeout/네트워크/비JSON/5xx → 저장 여부 미확인, 동일 요청으로 확인/재시도
```

### 6.2 Provider 변경

- `ledgerApi.createTransaction()`의 유효한 성공 결과가 거래 저장의 성공 기준이다.
- transaction ID로 insert-or-replace해 멱등 재시도 응답이 state 배열에 중복되지 않게 한다.
- summary/plan 갱신은 독립적으로 처리한다. `Promise.allSettled` 또는 각 catch로 각각의 stale/error 상태를 표시하고 성공한 자원은 갱신한다. 무조건 오류를 무시하지 않는다.
- summary/plan이 실패해도 이미 확인된 transaction 결과를 반환한다. “저장 완료, 요약을 새로 불러오지 못했어요”와 재조회 액션을 표시한다.
- 초기 `refresh()`도 profile·거래·계획의 오류를 하나의 profile 오류로 오인하지 않도록 점검한다. 데이터 없음과 조회 실패를 구분한다.
- update/delete/profile save도 후속 summary 조회 예외가 이미 성공한 mutation을 실패로 바꾸는지 같은 기준으로 처리한다.
- save 후 전체 거래 배열을 조회 결과로 덮을 때 오래된 응답이 방금 저장한 거래를 제거하지 않도록 stale-response 방지를 검증한다.

### 6.3 초안·멱등성·재시도

- 저장 직전의 payload/operation ID/선택 날짜를 하나의 사용자별 draft로 다룬다. 스키마 version을 추가해 기존 draft를 읽을 수 있게 한다.
- `localStorage` 읽기/쓰기/삭제 실패는 금융 저장 성공 여부와 분리한다. 메모리 초안은 유지하고 로컬 보관 실패를 정직하게 알린다.
- 요청 중 연속 탭, Enter, 이벤트 중첩을 막는다. disabled 외에 in-flight guard가 필요한지 테스트한다.
- 응답을 잃은 요청은 **동일 payload + 동일 operation ID**로 재시도한다. 실패할 때마다 새 ID를 발급하면 중복 거래 위험이 있다.
- 상태 불명 요청의 값을 바꾼 채 같은 ID로 보내지 않는다. 서버가 이전 결과를 반환할 수 있다. 원래 요청을 재확인한 후 해당 거래 수정으로 이동하거나, 서버가 미저장을 확정했을 때 새 논리 작업을 만든다.
- 저장은 성공했지만 초안 삭제가 실패하면 메모리/가능한 저장소에 완료 상태를 표시해 재진입 때 새 거래로 재전송하지 않는다. 보관할 수 없다면 재조회 확인 경로를 사용한다.
- 성공 후 URL date는 사용자 달력 날짜로 유지한다. 현재 서버 입력은 KST 정오 ISO 변환을 사용하므로 보존하면서, 반환 거래 날짜와 `transactionDateKey`로 월 경계를 검사한다. UTC의 문자열 앞 10자리로 달력 날짜를 단정하지 않는다.

### 6.4 오류별 UX

| 상황 | 표시 / 다음 행동 |
|---|---|
| 금액/날짜/계좌 400 | 해당 필드에 이유와 수정 방법, 초안 유지. 유효한 값만 재전송 |
| `invalid_account` | 현재 사용 가능한 계좌를 다시 불러와 선택하게 함. 존재하지 않는 cash 계좌를 임의 생성하지 않음 |
| 401 | 지원되는 세션 복원 절차 후 실패하면 재로그인 안내. 재전송은 같은 멱등 키. 사용자 전환 시 초안 격리 |
| `profile_required` 409 | 예산 설정을 완료하도록 안내. 설정 후 원래 입력을 안전하게 재개 |
| `pending_reason_required` 409 | 해당 대기 거래로 연결하는 버튼 제공. 실제 저장되지 않은 새 거래를 저장 완료로 표시하지 않음 |
| AI quota 429 | AI 한도/조회 실패를 정확히 설명하고 거래 저장 여부 확인. 일반 네트워크 오류로 덮지 않음 |
| 네트워크/5xx/응답 파싱 실패 | “저장 여부를 확인하지 못했어요” + 입력 유지 + 확인/같은 요청 재시도. `navigator.onLine`만으로 서버 상태 단정 금지 |
| POST 성공 + 요약 조회 실패 | 캘린더로 이동, 거래 표시, 요약만 갱신 대기/재시도. 금액을 0으로 대체하지 않음 |
| 미리보기 실패 | 현재 입력 유지, 미리보기 재시도. 확정 비활성 |

API 원문 오류를 그대로 사용자에게 노출하지 않는다. `ApiError`에 안전한 correlation ID를 유지하되 제품 화면에는 짧은 문의용 오류 번호가 필요한 경우에만 보조 노출한다.

### 6.5 backend 변경 경계

- `ledger/api.py`, `ledger/application/service.py`, `ledger/adapters/redis_store.py`, `ledger/quota.py`를 원인에 따라 추적한다. 이번 명세만 보고 저장소 migration이나 인증 신뢰 설정 변경을 하지 않는다.
- POST가 실제 실패한다면 인증·계좌 검증·저장·AI·plan impact 중 실패 지점을 재현하고 그 최소 범위를 고친다.
- 거래 기록 후 AI 처리 예외/연결 중단도 같은 ID 재시도로 거래가 하나만 남아야 한다. 기존 암호화·사용자 lock·멱등 캐시 계약을 유지한다.
- 한도 오류에서도 기록을 허용하도록 정책을 바꿔야 한다면 별도 `PLAN.md` backend 계약 작업으로 명시한다. 기존 quota 테스트가 거절을 의도하는지 확인하고 승인된 기록/AI 분리 동작을 문서화한다. 무료 한도를 우회하거나 인증 검사를 끄지 않는다.
- 기존 서비스 계층 내 작은 수리로 해결될 때 새 비동기 시스템/큐를 도입하지 않는다. 기록과 AI 지연 문제를 새로운 대규모 아키텍처 과제로 바꾸지 않는다.

## 7. 계획 검토 상태 규칙

현재 `preview` 존재 여부만 보는 로직을 바꾼다.

- `draftRevision` 또는 정규화한 draft fingerprint, `baseVersion`, `requestId`로 어떤 입력을 검토했는지 추적한다.
- 사용자가 필드를 바꾸면 기존 preview의 유효성을 취소한다. 새 요청 시작 전에 `preview/revisionPreview/error`를 일관되게 정리한다.
- 늦게 도착한 이전 요청은 현재 요청을 덮지 못한다. 컴포넌트 이탈·다시 수정도 포함한다.
- 확정 조건: 현재 요청 성공, 현재 초안과 미리보기 일치, 현재 baseVersion 일치, 저장 중 아님.
- 확인 화면의 수치와 실제 전송 payload가 같음을 검사한다. preview API는 저장하지 않으며 확인 버튼만 activate/apply를 호출한다.
- 409 버전 충돌은 최신 계획을 다시 불러와 재검토하도록 한다. 자동으로 사용자 예산을 덮어쓰지 않는다.
- 일반 초안 저장, preview, activation의 실패를 다른 안내로 구분한다. 일괄 “계획 저장 실패”로 덮지 않는다.

| 캘린더 | 오늘/이전 달/연도 경계, 날짜 추가, 검색/필터/목록 전환 | 선택 날짜 일치, 새 거래 표시, 총액 정확, 월 이동 후 복귀 정상 |
| 상세/이유/판단 | 보기/편집/삭제/평가, 이유 나중에, 실패 | 저장 결과 정확, 올바른 날짜 복귀, 일반 모드 끊김 없음 |
| 계획 1~3 | 기간 역전, 초안 복원, 예정 지출 편집, back/재검토 실패 | 넘침/과한 공백 없음, 현재 preview만 확정 가능 |
| 활성 계획 | 부족액, 긴 이름, 연결 실패, 버전 충돌, 유지/조정 | 결정론적 수치 유지, 실제 입력 기반 설명, 안전한 재시도 |
| 리포트 | 데이터 없음/많음, 큰 금액, 목표명 길음 | 빈 상태 정직, 차트/텍스트 넘침 없음, 원래/현재 계획 분리 |
| 설정 | 예산/목표 수정·취소, 계좌 추가/숨김, 말투, 로그아웃 | 기존 계정 편집 가능, 의미 없는 이동 없음, draft 격리 |
| 공유 | 미리보기/이미지 생성, 긴 문구 | 라벨·Canvas 모두 새 서비스명, 공유 민감정보 제외 유지 |

크기: 320, 360, 375, 390, **414**, 430, 768, 1280 CSS px. 핵심 홈/입력/계획은 전 크기; 나머지는 375/414/1280 + 위험한 상태를 우선한다.

환경: Chromium 모바일 크기, WebKit 또는 iOS Safari, 설치된 WKWebView. iPhone 실기기 결과와 시뮬레이터 결과를 분리한다.

경계값: 0/1/9,600/9,999,999/서버 허용 최대 금액, 30자 목표명·상호명, 큰 글자/200% 확대, 키보드 열린 상태, 날짜 picker 열린 상태, 가로 회전, 빈 목록, 오프라인 후 복구.

기하 검증:

- document scrollWidth ≤ clientWidth + 1px.
- 입력/버튼 bounding box가 부모 카드 content box 안에 위치; 그림자·의도된 FAB는 별도 처리.
- 헤더 프로필과 제목/설명 bounding box 교차 없음.
- 폼 제목→진행바→첫 필드 간격이 설계 간격을 따름; 5px 바의 그리드 행이 수십 px로 늘어나지 않음.
- 마지막 필드/CTA를 스크롤해서 완전히 노출 가능; bottom nav, keyboard, home indicator와 터치 영역 충돌 없음.
- 접근성 이름, focus-visible, 오류 연결 `aria-describedby`, 상태 live region, 모달 focus 복귀를 확인.

자동 테스트 요구:

1. 실제 `LedgerProvider` + API mock 조합으로 POST 성공 이후의 예외를 검증. `useLedger`를 전부 mock한 페이지 테스트만으로 끝내지 않는다.
2. 과거 월 저장 → 날짜 쿼리 → 선택된 일별 목록 → 새로고침까지 테스트.
3. 동일 작업 재시도는 저장/화면에 한 ID, 성공 뒤 새 거래는 새 ID.
4. storage set/remove 예외, 다른 계정, 로그아웃 후 복원 정책.
5. 미리보기 성공→입력 변경→재검토 실패, 응답 역전, 버전 충돌에서 확정 차단.
6. 예산/목표 수정 route 진입·저장·취소, 신규 실제 계정과 데모 구분.
7. 금액/날짜 경계는 서버 계약과 동일하게 검사. CSS는 jsdom 대신 실제 렌더러 측정.

명령 기준:

```bash
# frontend 디렉터리에서
npm test
npm run lint
npm run build

# 저장소 루트에서; backend 변경 시 필수
python3 -m unittest discover -s tests -v
python3 -m compileall ledger tests
git diff --check
```

Redis 테스트 skip은 live storage 검증 완료가 아니다. backend가 바뀌면 기존 격리 Redis integration 검증도 수행한다. 외부 AI 실호출은 별도 필요/승인 범위 안에서만 실시한다.

## 11. 이번 턴에 실제 수행한 검증

- 기준 커밋과 코드/기존 명세를 확인했다.
- 임시 합성 Vitest 진단 **5/5 재현**: summary 실패, plan 실패, storage 삭제 실패, 캘린더 날짜 누락, stale preview 확정 가능. `current-behavior.repro.tsx`는 **결함이 존재함을 확인하는 테스트**라 green이 정상 제품을 의미하지 않는다. 실행 후 frontend 임시 파일은 제거했다.
- 로컬 Chromium 414×896 합성 데모로 홈/계획 편집/거래 입력/장부/리포트/설정 6개 화면을 캡처했다. plan 5px 막대의 94px grid row를 측정했다. 6개 화면 document width는 414px; iOS의 date 넘침을 Chromium에서 재현했다고 주장하지 않는다.
- 실계정 POST, Render 로그/저장 데이터, 새 authenticated 저장 E2E, iPhone 원격 조작은 이번 턴에 수행하지 않았다. 사용자 제공 S1~S3가 실기기 결함의 증거다.
- 제품 코드 수정, production 배포, 공급자 설정 변경은 하지 않았다.
